۱. هدف پروژه

سامانه‌ای برای ثبت راننده، ایجاد سفارش، تخصیص نزدیک‌ترین سفارش سازگار با نوع وسیله، پیگیری مراحل تحویل، محاسبه درآمد و ارائه گزارش طراحی کنید. هدف تنها اجرای برنامه نیست؛ ساختار کلاس‌ها، کپسوله‌سازی، رفتار قابل‌آزمون و درک کد نیز ارزیابی می‌شود.

این متن قرارداد اجرایی یکسان پروژه است. منطق پایه از مسئله کوئرا الهام گرفته شده، اما کلاس‌های پایتونی، Propertyها، خروجی متدها و قواعد تست مشترک در این سند تعریف شده‌اند. در صورت تفاوت با جزئیات کوئرا، برای تست متقابل دانشجویان این سند ملاک است. رابط متنی main.py باید دستورات کوئرا را نیز پیاده‌سازی کند.

۲. قواعد داده و اصطلاحات

  • دسته وسیله: BIKE، VAN یا TRUCK (به حروف بزرگ).
  • وضعیت راننده: FREE یا BUSY؛ وضعیت اولیه FREE.
  • وضعیت سفارش: PENDING، ARRIVED، PICKUP، DELIVERED؛ وضعیت اولیه PENDING.
  • مکان: tuple دقیقاً دو عدد صحیح (x, y)؛ مقادیر bool پذیرفته نمی‌شوند.
  • نام کاربری: رشته غیرخالی از حروف انگلیسی و رقم، حداکثر ۲۵ کاراکتر، حساس به بزرگی/کوچکی حروف.
  • هزینه و اعتبار: همیشه Decimal از decimal؛ مقدار ابتدایی Decimal('0').
  • فاصله Manhattan: abs(x1-x2) + abs(y1-y2).
  • هزینه سفارش: Decimal(100) * Decimal(k + d)؛ d فاصله مبدأ تا مقصد و k شمار سفارش‌های PENDING همان دسته با احتساب سفارش تازه است. هزینه پس از ثبت ثابت می‌ماند.
  • انتخاب در فاصله برابر: ترتیب ثبت قدیمی‌تر اولویت دارد.

۳. طراحی کلاس‌ها و Propertyها

۳.۱. Driver

همه Propertyها فقط خواندنی‌اند. کلاس Driver فقط اطلاعات همان راننده را مدیریت می‌کند و نیازی به شمارنده یا ویژگی کلاسی ندارد.

is_available(self) -> bool

فقط وقتی status == 'FREE' است، True برمی‌گرداند. سایر متدهای تغییر وضعیت می‌توانند در سطح داخلی تعریف شوند؛ اما نباید Setter عمومی برای این Propertyها ایجاد شود.

۳.۳. DeliverySystem

DeliverySystem()

سامانه در آغاز راننده و سفارش ندارد. هر نمونه اطلاعات و اعتبار مستقل دارد. دو Property فقط‌خواندنی company_credit -> Decimal (مقدار اولیه صفر) و total_drivers -> int (تعداد رانندگان ثبت‌شده در همین سامانه) الزامی‌اند. تعداد رانندگان از مجموعه رانندگان سیستم محاسبه شود؛ نگهداری اشیا در dict یا list آزاد است، اما ترتیب ثبت باید حفظ شود.

۴. قرارداد قطعی متدهای DeliverySystem

نام متد، ترتیب پارامتر و نوع خروجی را تغییر ندهید. تمام تست‌های متقابل بر اساس همین قرارداد نوشته می‌شوند.

متد (امضای دقیق) رفتار مورد انتظار
add_driver(self, username: str, position: tuple, service_category: str) -> bool ثبت موفق: True؛ نام تکراری: False، بدون تغییر system.total_drivers
create_order(self, service_category: str, starting_position: tuple, finishing_position: tuple) -> int \| None ثبت موفق: شناسه از ۱ و پیوسته؛ مبدأ و مقصد برابر: None، بدون مصرف شناسه
assign_next_order(self, username: str) -> int \| None تخصیص نزدیک‌ترین سفارش PENDING با همان نوع وسیله: شناسه سفارش؛ نبود سفارش سازگار: None
update_order_status(self, username: str, order_id: int, new_status: str) -> bool تغییر مجاز: True؛ وضعیت نامجاز یا سفارش متعلق به راننده دیگر: False
get_driver(self, username: str) -> tuple \| None (status, position, credit)؛ نام ناموجود: None
get_order(self, order_id: int) -> tuple \| None (status, assigned_username, cost)؛ نبود راننده: نام None؛ شناسه ناموجود: None
get_order_list(self, status: str) -> list[int] فهرست شناسه‌ها با ترتیب ثبت، یا []
get_driver_list(self, status: str) -> list[str] فهرست نام‌ها با ترتیب ثبت، یا []
get_near_drivers(self, position: tuple, count: int) -> list[str] حداکثر count راننده آزاد به ترتیب نزدیکی؛ در تساوی، ثبت قدیمی‌تر
count_orders(self, position: tuple, distance: int, endpoint: str) -> int تعداد سفارش‌ها در فاصله کمتر یا مساوی distance از مبدأ (START) یا مقصد (FINISH)، مستقل از وضعیت
get_nearest_pending_order(self, position: tuple) -> int \| None شناسه نزدیک‌ترین سفارش PENDING بر اساس مبدأ؛ در تساوی، قدیمی‌تر؛ در نبود، None
get_company_credit(self) -> Decimal اعتبار فعلی شرکت

۵. چرخه سفارش و پرداخت

  1. create_order یک سفارش PENDING با هزینه محاسبه‌شده ایجاد می‌کند.
  2. assign_next_order تنها در صورت FREE بودن راننده، نزدیک‌ترین سفارش سازگار را برمی‌گزیند، سفارش را ARRIVED می‌کند، راننده را BUSY می‌کند، و ارتباط دوطرفه Driver.current_order و Order.assigned_driver را برقرار می‌کند. موقعیت و اعتبار تغییر نمی‌کنند.
  3. update_order_status(username, order_id, 'PICKUP') تنها از وضعیت ARRIVED قابل اجراست؛ موقعیت راننده را به starting_position تغییر می‌دهد.
  4. update_order_status(username, order_id, 'DELIVERED') تنها از وضعیت PICKUP مجاز است؛ موقعیت راننده را به finishing_position تغییر می‌دهد؛ ۸۰٪ مبلغ به راننده و ۲۰٪ به شرکت با Decimal('0.8') و Decimal('0.2') اضافه می‌کند؛ راننده FREE شده و current_order برابر None می‌شود. assigned_driver در سفارش برای سابقه باقی می‌ماند.
  5. تکرار تحویل، پرش مرحله و هر انتقال غیرمجاز نباید اطلاعات یا اعتبار را تغییر دهد.

۶. اعتبارسنجی و خطاها

  • نوع نامعتبر: TypeError؛ مقدار نامعتبر: ValueError. مکان غیـر tuple = TypeError؛ طول نامعتبر مکان = ValueError؛ مختصات غیـر int (از جمله bool) = TypeError.
  • دسته وسیله خارج از سه مقدار مجاز و نام کاربری با فرمت نامعتبر = ValueError؛ نوع نادرست آن‌ها = TypeError.
  • order_id باید int مثبت، count و distance باید int غیرمنفی باشند (bool مجاز نیست).
  • endpoint فقط START یا FINISH؛ مقادیر وضعیت باید متعلق به وضعیت‌های تعریف‌شده باشند.
  • اگر راننده در assign_next_order مشغول باشد: RuntimeError.
  • اگر نام راننده در assign_next_order یا update_order_status وجود نداشته باشد: KeyError.
  • در شرایطی که برای یک متد صریحاً False یا None تعریف شده، همان خروجی برگردانده شود، نه Exception.
  • هر عملیات ناموفق باید بدون تغییر حالت سامانه باشد. برای نام کاربری تکراری و مبدأ/مقصد یکسان پس از اعتبارسنجی ورودی، خروجی قراردادی اجرا می‌شود.

۷. اصول شی‌گرایی الزامی

  • مسئولیت‌های Driver، Order و DeliverySystem از هم جدا باشند؛ منطق کسب‌وکار در main.py قرار نگیرد.
  • اطلاعات داخلی با پیشوند _ ذخیره شوند؛ Propertyهای جدول فقط خواندنی باشند. مثلاً driver.credit = Decimal('1000') باید AttributeError ایجاد کند.
  • به‌کارگیری Class Attribute، @classmethod و @staticmethod الزامی نیست. total_drivers و company_credit هر دو از طریق Property فقط‌خواندنی یک نمونه DeliverySystem ارائه می‌شوند؛ هر سامانه داده مستقل خود را دارد.
  • کلاس‌ها باید بدون input()، print() یا راه‌اندازی رابط کاربری قابل import و تست باشند.
  • تعریف کلاس‌های کمکی، متدهای کمکی و ساختار داخلی آزاد است؛ قرارداد عمومی فوق ثابت است.

۹. Unit Testing و تست قرارداد مشترک

  • هر دانشجو دست‌کم ۱۵ تست مستقل با unittest می‌نویسد؛ شامل مقداردهی، خطای ورودی، سفارش، هزینه، تخصیص، تساوی فاصله، چرخه وضعیت، پرداخت، Property و جست‌وجو.
  • برای قابلیت خلاقانه نیز حداقل ۳ تست جداگانه لازم است.
  • فایل test_contract.py یک مجموعه تست پایه عمومی است؛ باید بدون تغییر در کنار سه فایل اصلی قرار گیرد و موفق اجرا شود.
  • موفق شدن تست‌های عمومی به معنای کامل بودن پروژه نیست؛ دانشجو موظف است تست‌های مستقل بیشتری طراحی کند.
python -m unittest test_contract -v
python -m unittest discover -s tests -v

۱۰. Peer Testing — ارزیابی متقابل

هر دانشجو باید تست‌های مستقل خودش را روی پروژه حداقل دو دانشجوی دیگر که مدرس تعیین می‌کند اجرا کند.

  • تست‌ها ابتدا روی پروژه خود دانشجو نوشته و در GitHub ثبت شوند؛ سپس پروژه‌های دیگر تخصیص داده می‌شوند.
  • تغییر کد دیگران برای موفق شدن تست‌ها ممنوع است.
  • هر شکست باید بررسی شود؛ ممکن است اشکال از تست باشد، نه از کد هم‌کلاسی.
  • گزارش هر ارزیابی باید نام مخزن، اسم تست، رفتار مورد انتظار، نتیجه واقعی و تحلیل را داشته باشد.
  • وجود نداشتن خطا نیز باید با گزارش تست‌های اجراشده مستند شود.
  • ارزیابی این بخش بر اساس دقت تحلیل و کیفیت تست‌ها است، نه تعداد خطاهای اعلام‌شده.

۱۱. قابلیت خلاقانه الزامی

هر دانشجو حداقل یک قابلیت رفتاری جدید بر اساس ایده خودش طراحی کند؛ مانند لغو سفارش، انعام، امتیازدهی راننده، تخفیف یا گزارش عملکرد. قابلیت باید با طراحی شی‌گرا سازگار باشد، API اصلی را تغییر ندهد و در README مشخصات، ورودی‌ها، خروجی‌ها، محدودیت‌ها و دست‌کم سه تست آن مستند شود. صرفاً تغییر ظاهر یا پیام خروجی، قابلیت جدید محسوب نمی‌شود.

۱۲. دفاع شفاهی و آزمون عملی

تحویل GitHub بدون دفاع حضوری کافی نیست. در جلسه دفاع (حدود ۱۰ تا ۱۵ دقیقه)، دانشجو باید معماری، Propertyها، تخصیص سفارش، تست‌ها، قابلیت خلاقانه و گزارش Peer Testing را توضیح دهد. مدرس ممکن است یک باگ معرفی کند یا از دانشجو بخواهد تغییر کوچکی در کد خود بدهد و تست مناسبی برای آن بنویسد. آزمون عملی بدون کمک دیگران و بدون ابزار هوش مصنوعی انجام می‌شود.
